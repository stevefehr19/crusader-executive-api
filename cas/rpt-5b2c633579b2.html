NOT A SECOND CONTROL PLANE AND NOT A SECOND SOURCE OF TRUTH. Every value is read
from the Command Center index, which is built from the CAS and Trading planes.
The publisher has no write path and opens no business plane. The API is built
into the SAME staging tree as the report portal and swapped in with it.

THE PUBLICATION BOUNDARY IS NARROWER THAN THE INDEX

ALLOW-LISTED, NOT REDACTED. Each projection names the fields that leave the local
machine, one at a time. Local paths, inbox paths, document paths and report
bodies are structurally absent, not filtered.

A WITHHELD RECORD IS COUNTED, NOT DROPPED. Every feed carries a withheld array
with the record identifier and the reason category; the text never leaves. A feed
that silently omits a row reads as "there is nothing there". Current count: zero.

CLIENT NAMES ARE TREATED AS SECRETS. The client list is loaded from the CAS
estate at build time, so a client signed tomorrow is protected without anyone
updating a list, and any record naming one is withheld.

THREE DEFECTS FOUND WHILE VERIFYING, ALL FIXED

1. THE API ROOT RETURNED 404 WHILE THE REPORT PUBLISHED IT AS THE ENTRY POINT.
All thirteen documents answered 200; the root did not, so the first address an
officer opened was the one that did not exist. The negative suite had measured
that 404 and scored it as a PASS, on the reading that it proves there is no
directory listing. That reading is true; it is also the reading of a reader who
was simply refused, and a test that scores an outage as a security win converts a
defect into reassurance. Fixed with a curated page rendered from the same
registry the JSON index is built from. Directory listings are still refused. An
explicit robots.txt was added for the same class of reason.

2. A REBUILD WAS DEMOTING REPORTS ALREADY PROVEN LIVE. The ledger compared state
as well as content, so after a report was confirmed PUBLISHED the next rebuild
recorded it as BUILT again and superseded the PUBLISHED row - 288 rows per report
per day, each erasing the fact that a stranger fetched those exact bytes. Fixed
narrowly; changed bytes still get a new version.

3. THE CONTENT HASHES WERE CHURNING EVERY FIVE MINUTES. Eight of thirteen
endpoints changed hash in forty-four seconds purely from restated clock readings,
so updated_at answered "did anything change?" with "everything, constantly".
Fixed: the hash strips raw clock readings at every depth and no more than those.

ONE CHANGE TO EXISTING CONFIGURATION

The deployment scope pinned the portal to two reports from a finished test. A
scope that survives its mission silently excludes every future release, which is
the dependency this directive exists to remove. It was removed. NOT a

OPEN ITEM - REPUBLISH, NOT PUBLISH

THE FIVE-MINUTE INDEXER REBUILDS. IT DOES NOT DEPLOY. Pushing to the public host
needs a hosting token that does not exist on the machine, and creating or
entering a credential is not an agent's action. So the API is live and correct
and will go stale between deploys. Three things make that safe rather than quiet:
every document carries generated_at and the index publishes a freshness contract;
the global status endpoint carries index freshness for both businesses; and the
publish script says NOT DEPLOYED rather than pretending.
